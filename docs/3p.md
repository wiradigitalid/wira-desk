### 2026-08-21 — the three inventories now reconcile against the code, 0 gaps

The inventory engine had nothing to compare against: the three artefacts were authored as prose
tables with no frontmatter and no `## Rows` section, so every derived row read as "present in code
but not recorded". That was one structural finding wearing 32 costumes.

Each artefact now carries frontmatter (`derived_from: code`) and a machine-maintained `## Rows`
section, written by `inventory.py` from this product's own readers. The authored sections above it
are kept and are not a duplicate: they carry transport, payload, semantics, and failure behaviour
that six derived columns have no room for, and that no pattern can read out of source. `## Rows`
answers *what exists*; the prose answers *how it behaves*.

Two things worth keeping from doing it:

- **The reader's `key` must be exactly what the engine derives from the first cell.** Mine built
  `config.toml#general` while the engine's comparison built `config.toml [general]`, so all five
  database rows reported as *both* missing and extra — ten findings about a file that agreed with the
  reader perfectly. A key contract that is nearly right is worse than an obvious mismatch, because
  the report looks like drift.
- **`platform_rows:` is deliberately not declared.** It names rows with no Product Component promise
  behind them, and declaring it would oblige `cross-cutting.md` to document each one. Every row
  already carries its owner in a column, so declaring it would have bought a documentation
  requirement and no information.

Row numbering was reset to start at 1. The engine's stability rule protects *published* numbers, and
these had only ever existed in an uncommitted intermediate state produced by the key bug above.

Also generated `timeline.yaml` and `report.yaml`, which retires the V14 skip. The validator now
skips only V19 (retrospective advisory at size M, stated) and V27 (an empty project room, a valid
state).

### 2026-08-21 — G3/G4 lens review: structure, prose, edge-case-hunter

Ran the lens set the owner's `risk_accepted: medium` selects, over both SRS and both SDD with their
slots, and the spine at structure/prose. Thirteen findings, all resolved in place except one that
is not this repository's to fix:

- **A contract prescribed behaviour the implementation had deliberately rejected.** The reload
  contract's error table said "Retry once" on a failed post. `signal_reload` does not retry, and the
  SAFETY comment at the call site says why: the post is a nudge to re-read a file that is already
  written, so a failure is reported rather than retried. A builder following the contract would have
  added the retry the author had reasoned their way out of.
- **The Tier-3 flow denied the recovery its own scenario documents.** `flow-hook-death-tier3.md`
  ended with "no longer work until daemon restart", while the attached scenario and the hook state
  machine both describe the heartbeat re-registering the hook and clearing the toast latch with no
  restart. The same diagram also had the heartbeat thread re-registering the hook and setting the
  tray tier; a hook belongs to the thread that installed it, so re-registering it from the heartbeat
  thread would install a hook nobody drains — the one failure this design cannot detect.
- **Two production IPC messages were missing from the API inventory** (refresh-OK and shutdown).
  Refresh-OK is precisely the message that makes recovery restart-free, so its absence hid the
  recovery path from anyone reading the inventory rather than the code.
- **The window-management contract inventory pointed at a contract file that did not exist.** Written
  now, since `mode: deep` requires a spec per endpoint, and the heartbeat is a real boundary.
- **The two settings scenarios were on a different template from the two window-management ones**,
  with no frontmatter at all — no type, id, component, or parent use case. Rewritten onto the shared
  shape. Both also carried the auto-start ownership error: one had the settings process reading a
  `schtasks` exit code it cannot see, and named a config key (`auto_start.enabled`) that does not
  exist. One claimed Save is disabled for an invalid field; Save is unconditional, and rejection
  surfaces as feedback.
- **A VM-bypass step cited the diagnostic-log business rule as its authority.** No cross-component
  rule governs the bypass; the decision invariant alone does.
- **A state-machine section was filed under the wrong entity.** The hook instance's lifecycle carried
  the name of the command entity, whose own lifecycle is three states in the domain model. Two
  machines under one name is how a reader ends up hunting `Degraded` in the wrong table.
- Softened two unfalsifiable performance absolutes in a design summary ("within microseconds",
  "sub-millisecond execution time") to the budget that is actually measured.

### 2026-08-21 — G3/G4 review: corpus reconciled against shipped code

Reviewed the five binding artifacts (spine, both SRS, both SDD) by verifying their claims against
source rather than reading them for coherence. SDD-window-management's eleven "Verified" rows all
held: `RING_BUFFER_CAPACITY = 16`, `ANTI_MACRO_THROTTLE_MS = 50`, `HOOK_HEARTBEAT_SECS = 10`,
`HOOK_CHECK_FAIL_THRESHOLD = 3`, `HOOK_RETRY_MAX = 5`, the toast latch, `suppress_start_menu`,
`TokenElevation`, `SetDllDirectoryW`, `TaskbarCreated`, and the `1..=5` command enum. Every cited
file exists. The defects were all in documents that had never been checked against the code they
describe — the corpus was harvested from the 2026-07-06 BMAD plan, and the implementation had moved
on or had never matched it:

- **BR-5 and FR-12 described a mechanism that never existed here.** Both said "View Logs" opens the
  log *folder*, and BR-5's enforcement quoted `ShellExecuteW(..., L"explore", log_dir, ...)`.
  `git log -S '"explore"'` returns exactly one commit — the corpus commit. `menu.rs::view_logs`
  has spawned `notepad.exe <log_path>` since the initial public release. Corrected to the file, and
  FR-12's proof-of-done with it: a wrong proof either fails G5 against working code or provokes a
  code change to satisfy a promise nobody made.
- **The auto-start task name was wrong in three places.** `WiraDeskAutoStart` in `business-rules.md`,
  `domain-model.md`, and the PRD; `shared::constants::TASK_NAME` is `"WiraDesk"`. Had a wave
  implemented BR-4 as written, `/Create` and `is_registered`'s `/Query` would have disagreed and the
  menu checkmark would never have lit.
- **Auto-start ownership was attributed to `settings`.** BR-4's enforcement, SRS-settings' constraint,
  the SDD's structure table, its dependency diagram, and UC-6's flow all had the settings process
  calling `schtasks`. `grep schtasks` hits `crates/daemon/` only: settings writes
  `general.auto_start` and signals reload; the daemon reconciles the task, and `schtasks /Query` is
  authoritative for the checkmark.
- **The spine's Stack table was stale on all three pinned crates.** `windows-sys` 0.59.x → 0.52,
  `egui`/`eframe` 0.31.x → 0.35, `toml` 0.8.x → 1.1 (moved by #5, never reflected here).
- **SRS-window-management listed `SetWindowPos` as a non-blocking enumeration API.** It is a mutation
  API belonging to the arrangement engine; replaced with the spine's actual sterilization list.
- Smaller: SRS-WM's success signal claimed "under 1 ms perceived latency" against NFR-2/NFR-3's
  10 ms hook budget; SRS-settings undercounted its local rules as `LBR-ST-1..5` when seven exist,
  and its gate checklist omitted two of the decision invariants its own Constraints bind; both SRS asserted
  requirements were "ratified at G3" while `gates_passed` read `[G1, G2]`.

No `DEC-` was written for any of these. `decision-guide.md`'s test is whether the answer is readable
from the code in three months, and in every case it is (`menu.rs::view_logs`, `TASK_NAME`,
`daemon/src/autostart.rs`, the manifests). Recording them would have been backfilling from memory,
which the guide forbids.
