### 2026-08-26 — Slint accepted under its royalty-free branch, and what that obliges

The Slint migration made `cargo-deny` fail the `licenses` check, and the failure was correct rather
than pedantic. Slint is tri-licensed — `GPL-3.0-only OR LicenseRef-Slint-Royalty-free-2.0 OR
LicenseRef-Slint-Software-3.0` — and none of the three was in the allow-list, so the gate did the
one thing it exists for: it refused a copyleft licence entering an MIT product by accident.

The royalty-free branch is now accepted in `deny.toml`. A `cargo-deny` allow entry satisfies an `OR`
expression by naming one branch, so this is a choice among three, not a blanket permission. Why not
the other two is recorded beside the entry: `GPL-3.0-only` would pull the distributed work under
copyleft and contradict `LICENSE`, and the commercial branch sells a per-device royalty that exists
for embedded use, which this product is not.

**What is not obvious from the diff:** the accepted branch carries an obligation, and the obligation
lives in files that look cosmetic. The licence requires the use of Slint to be disclosed on a public
page where the binaries can be found. Two places now carry it — the `## Built with Slint` section in
`README.md`, and the release notes composed in `.github/workflows/release.yml`. Deleting either as
clutter breaks the licence under which the dependency is used. Both say so in place, so the reason
travels with the text.

Two follow-ons from the same audit:

- `OFL-1.1` and `Ubuntu-font-1.0` were removed from the allow-list. They were there for
  `epaint_default_fonts`, which left with egui; verified absent across all 600 packages
  `cargo metadata` resolves. An allow entry no dependency needs is a rule that cannot fail.
- `NOTICE` was regenerated from `cargo metadata` — 439 entries to 600. It had been describing the
  egui dependency graph, which no longer exists.

Still red after this change, and left alone deliberately: `advisories` fails on two unmaintained
crates that arrive with Slint, and both need a recorded decision rather than a reflex `ignore`.

### 2026-08-25 — Shortcut collision handling corrected to match DEC-001 (applying G4 delta for `settings`)

Two defects found by `wdi-review` (edge-case-hunter lens) in the uncommitted shortcut-conflict UX
were fixed. Both existed only in the working tree — neither had reached a commit.

- **Save was gated on a standing conflict** (`crates/settings/src/main.rs`): `can_save =
  !has_any_conflict()` disabled the Save button, which is exactly what `DEC-001` (and SCN-01's
  prior reasoning) says not to do — a disabled button cannot say which of six fields disabled it.
  Removed; Save is always enabled, and `validate_config` already refuses an unusable draft at
  submission and already names both offending fields.
- **`Swap ⇄` was a proven no-op**: `find_conflict` only matches on equal values, so the button was
  only ever offered when the two fields already held the *same* string — swapping two equal
  strings is the identity. The pre-existing test hid this by clearing the conflict before calling
  swap. Fixed by having `SettingsModel` remember the chord a capture displaces
  (`last_capture: Option<(ShortcutField, String)>`); `swap_shortcuts` now gives that displaced
  chord back to the collision partner, and is only offered (`can_swap`) on the row whose capture
  actually caused the conflict — the partner lost nothing and has nothing to swap back.
- **Conflict messages named TOML keys, not actions**: a save-time rejection read
  `"switcher.fallback_shortcut conflicts with switcher.shortcut"`. `ShortcutField::key()` /
  `from_key()` added so `describe()` resolves a dotted config path back to its human label

  confusion `DEC-001` exists to end, previously surviving in a different spot.
- **A successful capture no longer leaves stale feedback standing**: `accept_capture` now clears
  `SaveFeedback` so a green "Settings saved and applied" banner cannot linger over a fresh
  collision.
- Guard test (`swap_gives_the_conflict_partner_back_the_chord_the_capture_displaced`) was verified
  red against the old identity-swap implementation before the fix, then green after, per this
  repo's mutation-testing rule — a test never seen red is a claim, not proof.
- `DEC-001` and `DEC-002` (`.control/decisions/`) applied against `.what/settings/` and
  `.how/settings/SDD-settings.md` (new `SCN-03`, `LBR-ST-8`, two SDD Failure Behaviour rows) in a

  `$env:WIRADESK_SKIP_MANIFEST = '1'; cargo test --workspace --no-fail-fast` all green — 344 tests

  `shortcut_conflict_detection_and_swap` test — which cleared the conflict before calling swap,

### 2026-08-22 — RISK-3 closed: the 0.36.1 accessibility claim is proven, not inherited

The eframe/egui bump to 0.36.1 replaced the AccessKit adapter that FR-20 and FR-21 had been
verified against, and `RISK-3` recorded the consequence: the build was proven while the
accessibility claim was inherited. This closes that gap by re-reading the live UI Automation
surface on 0.36.1 rather than trusting it.

Method worth keeping, because Orca's accessibility `treeText` is **not** sufficient on its own: it
carries role and name but no state, so a toggle looks identical checked or unchecked. The evidence
came from a `System.Windows.Automation` client reading `TogglePattern`, `ValuePattern`,
`RangeValuePattern`, `IsKeyboardFocusable` and `HasKeyboardFocus` per element, with Orca driving the
clicks and Tab presses. Raw captures are in `.work/a11y/`.

Every property FR-21 names survives the adapter change: pane tabs carry a TogglePattern, the
auto-start control is a `CheckBox` whose `toggle` flips live On/Off, the layout controls expose
`value='50'` and `range=[10..100]`, each shortcut button embeds its current value in its accessible
name, and arming a capture renames that button to "Listening for a key combination. Press Escape to
cancel." FR-20 was walked pane by pane -- General, Shortcuts and About match `focus_order` exactly,
and Shift+Tab reverses the cycle exactly.

Two results that look like defects and are not. `Revert` never appears in the Tab cycle while the
draft is clean, because it is disabled there. And every shortcut row publishes a `Text` label plus a
`Button` whose name repeats that label with the value appended -- verbose for a screen reader, but
the value has to live somewhere the reader will speak, and the name is that place.

One real deviation, recorded as `DEF-2`: `focus_order(Pane::Layout)` declares "Stack width percent"
as one stop while the tree publishes two focusable controls with that identical name, a `Slider` and
a `Spinner`. **`focus_order_mismatch` structurally cannot catch this** -- it compares the
declaration against the stops the renderer says it drew, so declaration and renderer agree with each
other while neither matches what assistive technology sees. That is the argument for automating this
check rather than repeating the manual pass on every egui bump, and it is recorded as RISK-3's
residual.

### 2026-08-22 — eframe and egui to 0.36.1, together, because apart they cannot compile

Dependabot raised these as two PRs (#7, #8) and both failed to build. The error looked like an API
break and was not:

    error[E0308]: expected `egui::Context`, found `eframe::egui::Context`
    note: there are multiple different versions of crate `egui` in the dependency graph

Raising `eframe` alone pulls `egui` 0.36.1 in through it while the direct `egui` stays 0.35, so
`cc.egui_ctx` and `theme::initialize(&egui::Context)` become two distinct types. Raising `egui`
alone is the mirror image. **Neither PR could ever have passed on its own**, and merging either
would have broken `main` — the kind of trap a split dependency bump sets for whoever merges first.

Done as one change instead: both to 0.36.1, **zero source changes**, which is the proof it was a
pairing problem rather than a migration. Verified here rather than taken from the worker: exactly one
`egui` in the lockfile at 0.36.1, fmt clean, clippy clean under `-D warnings`, `cargo test
--workspace` exit 0 with 330 passing.

`features = ["accesskit"]` survived, and that was the one thing worth guarding hardest: it is not a
default eframe feature, and losing it publishes no UI Automation tree at all while the window still
looks perfectly correct.

The `Cargo.toml` comment claiming a harness "freezes eframe 0.35.x" was traced before being
overruled. It comes from the accessibility contract story in the planning archive, whose criterion was that
Cargo metadata, the lockfile, and the architecture SSOT name **one** version and mechanism — aimed at stopping an older version being
silently retained, not at pinning 0.35 forever. The comment now names 0.36.x so it stops
contradicting the manifest three lines below it.

What the bump does not carry, recorded as `RISK-3`: the accessibility evidence. Roles, names,
values, and listening state were confirmed against the 0.35 AccessKit adapter, and nothing automated
stands behind FR-20 or FR-21 — `focus_order_*` proves the declared focus order, not the UIA tree. So
the build is proven and the accessibility claim is inherited. The spine's accessibility invariant now
states both the coupling rule and that obligation.

### 2026-08-21 — the bypass check got a test seam, so the suite stopped reading the desktop

`handle_key_event` asked the OS whether the foreground window belonged to a VM or Remote Desktop
guest the moment a chord matched. That is right in production — the question has no other answer —
but two unit tests called it directly, so with no resolvable foreground window the bypass failed
open, the matched chord returned pass-through, and both tests failed. They passed or failed
according to what had focus, and on a CI runner with no interactive desktop they would fail every
run.

Split into a thin `handle_key_event` wrapper plus `handle_key_event_with_bypass`, which takes the
check as an `FnOnce(&mut HookRuntime) -> bool`.

**A closure, not a `bool`, and that is the whole point of the shape.** Passing a pre-computed
boolean would have forced the live Win32 query to happen *before* the function knew whether a chord
had even matched — adding an OS call to every key event, on the one thread that must finish inside
`LowLevelHooksTimeout`. Deferring it keeps the call exactly where it was: after the match, on a rare
path. The generic is monomorphised, so the seam costs nothing at runtime.

Production behaviour is unchanged; the wrapper supplies the real call. The two tests pass `|_| false`
and keep every assertion and expected value they had — they guard the sticky-modifier bug, where a
swallowed Win key-up left the focused application treating every later keystroke as Win+key, so
weakening them to get green would have thrown away the guard and looked like a fix.

Verified here, not taken from the worker's report: `cargo fmt --all` clean, clippy clean under
`-D warnings`, `cargo test --workspace` **exit 0, 330 passing**.

One residual, left deliberately and recorded in `defects.yaml`:
`hook::tests::no_modifier_release_is_ever_swallowed` still calls the live path. Its assertion holds
on both branches — a bypassed chord never sets `swallow_release_vk`, so the modifier release passes
through either way — which means it would also pass if the bypass swallowed everything. That is
exactly the "passes for the wrong reason" shape `docs/decisions.md` warns about. Route it through
the same seam next time that file is open.

### 2026-08-21 — publication gate taught where the corpus lives

`scripts/verify-public-export.ps1` was red on `main` with 133 findings, and had been since the
commit before this one. The gate was aligned for `_bmad-output/`, `_bmad/`, the skill directories,
`.control/memlog/`, and `.constitution/method/` in f7f6585; the WDI corpus landed in a4860f1 and
nobody re-ran it. CI runs it on every push (`ci.yml`, "Publication hygiene"), so `main` was failing.

Two `Allowed` blocks now admit `.what/*`, `.how/*`, and `.control/*`:

- **internal vocabulary** — the same reason already recorded in the file for the planning archive.
  An architecture-decision or requirement identifier is opaque when it turns up in a README with
  nothing nearby to explain it. The spine is where those decision identifiers are *defined*, and the
  requirements registry is where the requirement identifiers are. The rule was written against
  references far from their meaning, and these are the meaning.
- **public claims** — the `_bmad-output`/`design-system` asymmetry, applied. The daemon RAM ceiling,
  quoted in the memory requirement, the brief's sizing table, and the spine's budget table, is a
  requirement target stated in the document whose job is to state targets. A release string in a PRD
  revision history is a document version, not a shipped release.

Neither pattern was touched, and `crates/`, `docs/`, and the root documents stay enforced — that
split is the rule, and widening the patterns instead would have been the failure the file warns
about. If either rule ever fires on product source again, it is a real finding.
