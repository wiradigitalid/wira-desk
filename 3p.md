### 2026-08-27 — auto-start was never broken; three schtasks defaults were, and one of them kills a running daemon

`schtasks /Query /TN WiraDesk /V /FO LIST` from a real install settled the reported
failure and then produced two defects nobody had looked for.

**The reported symptom was not a fault.** `Last Result: 267011` is `0x41303`,
`SCHED_S_TASK_HAS_NOT_RUN`, paired with the `30/11/1999` sentinel for never-run. Every
field that matters was correct: the action quoted and inside `%ProgramFiles%`, `Run As
User` the interactive user, `Logon Mode: Interactive only`, state `Ready`/`Enabled`. An
`ONLOGON` task simply had not been triggered yet.

**Three settings were wrong, and `schtasks.exe` has no flag for any of them.** Verified
against `schtasks /Create /?`: nothing for power management, nothing for execution
limits. `/XML` is the only CLI route.

* `DisallowStartIfOnBatteries` defaults **true**. Confirmed empirically on the reporter's
  laptop: plugged in, the daemon starts after a restart; on battery, it does not.
* `StopIfGoingOnBatteries` defaults **true**, so unplugging a charger *terminates* a
  running daemon. Worse than the first, because it strikes mid-session.
* `ExecutionTimeLimit` is **absent** from the XML Windows emits, and absent means the
  72-hour default — a kill switch on day three for a process meant to run indefinitely.
  Only visible in `/V /FO LIST`, as `Stop Task If Runs X Hours: 72:00:00`.

Registration now prefers `/XML` and falls back to flags. The fallback is the point: the
XML path depends on a staging directory passing an ACL check and on a schema this code
cannot validate locally, and if either gives way auto-start still registers with the old
defaults — the behaviour that shipped, which is a better floor than nothing.
`refresh_registered_path` already calls `enable` on every daemon start, so every task
written by an older version is corrected with no migration code.

**Where the XML is staged is a privilege boundary, and the obvious answers are wrong.**
`schtasks` reads the file back as an elevated process, and what it reads becomes a task
that runs elevated at every logon with no prompt. A file in `%TEMP%` or `%APPDATA%` can
be replaced by another process running as the same user between our write and that read,
which registers an attacker's task definition. Deleting the file afterwards does not
close it: the window is before the delete. Both locations sit in the user profile at
normal user permissions — `PRIVACY.md` already says so out loud. So the install
directory is used, and `acl::replaceable_by_non_admin` is asked rather than assumed:
anything short of `AdminOnly`, including an unreadable DACL, returns `None` and takes
the CLI path. Wrong battery settings beat a privilege escalation.

The element order mirrors what Windows itself emitted from `schtasks /Query /XML` for a
task created the old way, not a reading of the schema sequence — the two disagree about
where `MultipleInstancesPolicy` belongs, and output Windows produces is output Windows
accepts. `<Command>` is deliberately unquoted: the CLI form needs `"..."` so a spaced
path is not split into executable plus arguments, but in XML the element boundary does
that and quotes would become part of the path.

Escaping the five XML metacharacters is a guard rather than tidiness, because the install
path ends up inside a document that becomes an elevated logon task. It was seen red:
removing the `<` case fails `xml_escaping_closes_the_injection_route`.

**`run_schtasks` no longer throws away the explanation.** It discarded both streams on
the reasoning that only the exit code mattered, and the bill arrived the first time
auto-start misbehaved on a real machine — the log said `schtasks /Create failed` and
nothing more, so the cause had to be reconstructed by hand. Both streams are now
captured and logged on failure, collapsed to one line and clipped by characters rather
than bytes so a localised message cannot split a UTF-8 sequence.

**Not verified, and it cannot be from here.** No task was registered during this work:
creating one in the root folder needs elevation this session does not have, and the
probe returned `ERROR: Access is denied` rather than a schema complaint — which says
nothing either way about whether the XML validates. What is proven is the document's
content, by five tests, and that a failure falls back rather than breaking auto-start.
Whether Task Scheduler accepts it, and whether the daemon then starts on battery, needs
a machine with elevation.

### 2026-08-27 — the finish-page launch failed with error 740, because one Inno default flips on the presence of another flag

Reported from a real install: ticking "Start Wira Desk now" on the last wizard page produced

```
Unable to execute file ... CreateProcess failed; code 740.
The requested operation requires elevation.
```

The cause is a conditional default in Inno's `[Run]` section, quoted from its documentation:
without `postinstall`, `runascurrentuser` is the default and the entry inherits Setup's
elevated token; **with** `postinstall`, `runasoriginaluser` is the default and the entry runs
with the user's normally non-elevated credentials.

The finish-page checkbox is a `postinstall` entry, so it launched the daemon unelevated. The
daemon's manifest demands `requireAdministrator`, and `[Run]` uses `CreateProcess`, which
**cannot** elevate — only `ShellExecuteEx` can. So there was never going to be a UAC prompt to
fix this; the call fails outright. The intuition that it "should have asked" is exactly right
about what a user expects and exactly wrong about which API was in play.

Both entries now carry `runascurrentuser` explicitly. The redundancy on the silent entry is
deliberate: relying on a default that flips depending on whether a *different* flag is present
is what produced this bug, so neither entry depends on it any more.

`shellexec` would also have worked, by routing through `ShellExecuteEx` and raising a prompt.
It was rejected: Setup is already elevated with the user's consent, so a second prompt for the
same action is noise. Inheriting the token Setup holds costs no prompt at all.

**Note which path was broken, because it inverts the assumption in the entry above this one.**
Yesterday's fix added a second `[Run]` entry for the silent path, on the reasoning that silent
is the path nothing exercises by hand and therefore the path that breaks. That entry has no
`postinstall` flag, so it was already correct. The path that was broken is the wizard — the one
a person always takes, and the one that had existed unexercised since the script was written,
because nobody had run the installer until today.

Guarded by the compiler: renaming the flag to `runascurrentuserTYPO` fails the build with
`Parameter "Flags" includes an unknown flag`, so CI compiling the installer on every push
catches a future edit that drops or misspells it.

Two smaller facts from the same report, both worth keeping. Google Drive refused the installer
as "infected with a virus" while Defender on the build machine scanned it clean, which is the
shape of a single-engine heuristic hit rather than agreement between scanners. The product's
properties stack into the exact silhouette of a keylogger with persistence — unsigned, requires
admin, installs a global keyboard hook, registers an `ONLOGON /RL HIGHEST` task, zero
prevalence, wrapped by an installer format malware favours — and no heuristic engine will give
that combination the benefit of the doubt without a signature. That moves code signing from a
SmartScreen nicety to a distribution blocker: Drive is not the only channel that scans.

**Corrected within the hour, and the correction matters more than the original claim.** The
uninstaller was reported blocked by an application-control policy — `error 4551`, "unable to
execute file in temporary directory" — and this entry first recorded that as a product that can
be installed and then not removed through its own path. That was too strong. **Retrying the
uninstall succeeded.** The block is intermittent, not permanent.

The likely mechanism is that these checks are cloud-backed: Smart App Control and the ASR rule
that blocks executables lacking prevalence, age, or trusted-list membership ask Defender's cloud
for a verdict, and the first attempt **fails closed** while no answer has arrived. The retry
gets one.

Intermittent is worse than permanent for one specific path, and it is a requirement rather than
an observation. The updater runs the installer silently, so a launch blocked this way would
present as a progress bar completing and nothing happening — no error, no new version, the
silent-failure class again. **The updater must check the installer's launch result and surface a
failure with a retry**, rather than treating "spawned" as "succeeded". Signing still matters
here, but the accurate reason is that it removes a class of INTERMITTENT friction, and
intermittent friction on an update path is worse than an honest refusal.

### 2026-08-27 — the version collapsed from eleven literals to one, and the first fix for it failed in only one direction

The number lived in **eleven literals across five files**: three crate manifests, and two
resource scripts carrying four fields each. One test guarded one of them.

Now it is written once, in `[workspace.package] version`. The crates inherit it with
`version.workspace = true`, and each `.rc` receives it as preprocessor macros from its
`build.rs` through `embed-resource`'s macros parameter — which was already there in the call,
passed as `NONE`. The resource scripts hold no version literal at all.

`WD_STR` is two levels (`WD_STR_INNER(x) #x`, then `WD_STR(x) WD_STR_INNER(x)`) because a macro
cannot be pasted into `"..."` directly. With one level the literal text `WD_VERSION` lands in
the version resource and nothing at runtime notices, so the test asserts both levels are
present. The digits are passed separately rather than comma-joined, which sidesteps the question
of whether a macro definition containing commas survives a command line into the resource
compiler.

**`crates/settings/wiradesk-settings.rc` had never been guarded, and its comment said it was.**
It claimed `version_resource_matches_cargo_manifest` asserted the match; that test lives in the
daemon crate and reads the daemon's own script. Nothing checked the Settings one. And Settings
displays its version in the About screen from `CARGO_PKG_VERSION` directly, so the properties
dialog and the About screen could report different versions with the entire suite green. This is
the second time in two days that a comment in this repository promised a guard that did not
exist.

The old test is replaced rather than deleted: `resource_scripts_hold_no_version_literal` asserts
that neither script has had a literal written back into it, which is the only failure mode left
once the number is generated — and it covers both scripts.

**The first attempt at the rebuild trigger was wrong, and wrong in a way that would have
survived CI.** `cargo:rerun-if-env-changed=CARGO_PKG_VERSION` is not a trigger: cargo *injects*
that value rather than reading it from the environment, so the check compares unset against
unset and never fires. What made it hard to see is that the failure was one-directional.
Raising the version rebuilt correctly, because a new version also rewrites `Cargo.lock` and
that dirties the crate. **Lowering it did not** — the manifest said `0.1.0` while the embedded
resource still said `0.4.2`, `cargo build --locked` reported success, and the only place the
disagreement appeared was the properties dialog of the built binary.

CI is immune, because it always builds from a clean checkout. That is precisely what made this
a local-only trap: green everywhere it is measured, wrong on the machine of whoever bumps the
version and then tests. Both build scripts now declare
`cargo:rerun-if-changed=../../Cargo.toml`, and the previously failing direction was re-run and
observed correcting both binaries in one build.

It was found by mutation, not by reading — bumping to `0.9.7`, then `0.4.2`, then back, and
reading `FileVersion` out of both compiled executables each time rather than trusting that the
build succeeded. Testing only the upward direction would have shipped it.

**Two side effects of the consolidation, both handled at the source.** `cargo build --locked`
fails after a bump unless `Cargo.lock` is committed with the manifest, because the lock records
the workspace crates' versions — so `scripts/bump-version.ps1` refreshes it with
`cargo update --offline --workspace` and says, in its own output, that both files must be
committed together. And `scripts/verify-public-export.ps1` read the product version from
`crates/daemon/Cargo.toml`, which now says `version.workspace = true` and carries no number; it
was **redirected to the root manifest, not loosened** — same regex, still demanding three
numeric fields, made section-aware so a `version` under a different table cannot be mistaken
for this one.

`scripts/bump-version.ps1` is also where the ownership rule recorded in `AGENTS.md` becomes
mechanical: `-Patch` needs nothing, `-Minor` and `-Major` exit 2 without `-Owner`, and `-Set`
works out which digit moved and applies the same test. All four paths were exercised. It is a
speed bump and not a boundary — anyone can edit the manifest by hand — and the script says so,
because the failure it prevents is momentum, not malice.

**`CHANGELOG.md` is now Keep a Changelog, and `release.yml` refuses a tag without a section for
it.** The step runs before anything is built, extracts `## [x.y.z]` up to the next `## `, and
treats an empty section as a failure too. Both outcomes were tested: `0.1.0` extracts 1,673
characters, `0.1.1` and `0.2.0` are refused. That section becomes the release notes, and — the
reason it is worth a gate rather than a convention — the in-app updater will show it to a user
before they decide to update. `###` subheadings do not terminate the extraction, which was
checked rather than assumed.

Also synced: `AGENTS.md` to `CLAUDE.md` and `.agents/AGENTS.md`, byte-identical, on the owner's
go-ahead. `.agents/AGENTS.md` was three weeks stale.

Gates: `fmt` clean after one reformat, `clippy -D warnings` clean, 447 tests pass, publication
gate passes all ten content checks. `cargo deny` was **not** run — it is not installed locally
and arrives in CI as a checksummed download, so CI is where it runs.

### 2026-08-27 — gate 1 closed: Inno Setup ships, the NSIS script is gone, and the silent path was broken

Three decisions were taken, and the first of them was the one that could only be taken cheaply
before the first tag:

- **Inno Setup is the installer.** `packaging/wiradesk.nsi` is deleted rather than kept, because
  two packaging scripts where CI builds one is how a repository ships the one nobody has read in
  a year. Both workflows now build `packaging/wiradesk.iss`.
- **The updater lives in Settings, and verification rather than de-elevation is the control.**
  Settings inherits an elevated token today because the daemon launches it with `ShellExecuteW`.
  That is accepted for now: an attacker would have to defeat SHA-256 plus, once a certificate
  exists, an Authenticode publisher match — and the exposure is no worse than a user downloading
  and running the installer by hand. De-elevating Settings remains worth doing for its own
  reasons, but it is not a prerequisite for shipping updates.
- **The automatic update check is on by default and does not ask.** This is the owner's call,
  taken against the alternative of a first-run prompt. It has an unpaid consequence, recorded
  here so it is not lost: `PRIVACY.md` still states *"There is no socket, HTTP client, or update
  check in the source"*, and because there is now no consent moment anywhere in the flow, that
  document has to carry the disclosure by itself — what is sent, what it reveals, and where the
  off switch is. The off switch still exists in Settings; what the decision removes is being
  asked, not being able to decline.

**The substantive bug this uncovered has nothing to do with which compiler won.** The installer
never restarted the daemon after a silent install. `[Run]` had a single entry flagged
`skipifsilent`, which is correct for a wizard that has no finish page to hang a checkbox on —
and it meant that every silent install finished with the application not running. Silent is not
a corner case here: it is `winget install`, `winget upgrade`, and every update the application
performs on itself. The symptom would have been the worst kind, a user pressing Update, watching
a progress bar complete, and finding the application gone, with nothing logged and no error.

No manual test would have found it, because a person testing by hand always takes the wizard
path. The fix is a second `[Run]` entry gated on `Check: RunningSilently`, a one-line wrapper
over `WizardSilent`, so exactly one of the two entries fires. That the binding is real was
proven by mutation rather than by reading: renaming the function to `RunningSilentlyTYPO` fails
the compile with *"Required function or procedure 'RunningSilentlyTYPO' not found"*, which means
CI compiling the installer on every push actually guards this.

A related trap is now documented in the script instead of waiting to be rediscovered. Both the
old and the new installer run `taskkill /IM wiradesk-settings.exe`, and they must, because
`[Files]` replaces that executable and Windows cannot replace a running image. Since the updater
lives inside Settings, the installer kills its own launcher. The obligation is the updater's —
launch Setup detached, then exit — and the comment says so at the line where the tempting wrong
fix is.

**The version floor was implemented twice, because the first version could not pass.** It was
written as an assertion in the install step against `ISCC /?`, which never prints the version:
that output says only "Inno Setup 6", and the version resources of `ISCC.exe`, `ISCmplr.dll`,
and `Compil32.exe` are all `0.0.0.0`. So the check threw on its own first run — a gate that
cannot pass in the place it was written, which this repository has been caught by before. The
precise version appears in exactly one place, the compiler's banner while compiling, so the
assertion now runs there, against the compiler that actually just ran, and treats absence of
the line as failure rather than as a pass.

The pin itself does most of the work: a matching SHA-256 identifies the build bit-for-bit, so it
cannot be a vulnerable 6.2.1. The floor guards a future edit, not this one.

`9c73c3bae7ed48d44112a0f48e66742c00090bdb5bef71d9d3c056c66e97b732` is
`innosetup-6.7.3.exe`, verified by downloading it twice from independent invocations. It comes
from **GitHub Releases**, and that matters: `files.jrsoftware.org/is/6/innosetup-6.7.3.exe`,
which looks like the canonical path and is what a plausible guess produces, returns **404**.
That was found by checking the URL before committing it rather than by a failed release.
`/PORTABLE=1` is what makes the toolchain need no elevation and leave no machine state behind.

**Toolchain licence, checked rather than assumed.** Inno's compiler prints "Non-commercial use
only", which looks alarming for a product built by a company. Its licence says the opposite in
plain terms — permission is granted "to anyone to use this software for any purpose, including
commercial applications" — and the banner is a request to buy a commercial licence, added in
6.5.0, not a restriction. It is also compiler-only: searching the compiled installer for it
finds nothing. The condition that does bind is that binary redistributions retain the existing
copyright notice and web addresses, and that holds by construction: the produced Setup carries
"This installation was built with Inno Setup." and a `jrsoftware.org` URL. Both facts are now
written into the script, because stripping those strings would look like tidying up.

Two smaller things landed with it. `latest.json` is now published as a release asset — a name
that never changes, so `releases/latest/download/latest.json` is a permanently stable URL with
no API and no rate limit, read by both the updater and the download page so the two cannot
disagree. And the release notes no longer offer `winget upgrade` as the way to update: updating
is a button in Settings, whichever channel installed the product, and a user is never asked to
type a command to stay current.

**One earlier claim in `docs/packaging-choice.md` is overstated and corrected here.** Reading
the version from the binary was described as *deleting* the need for the tag-versus-crate check
in `release.yml`. It does not: it removes having to pass the version in, but the tag still names
the GitHub release and could still contradict the binary inside it, so that step stays. What did
come free is a cross-check in the other direction — the build step now asserts that the file
ISCC produced is named for the crate version, and since ISCC names it from the `.rc` version
resource, a drifted `.rc` now fails the release as well as the test suite.

Verified: the build step was run verbatim from the repository root with a relative script path,
which is how CI invokes it, and it compiles with no warnings and produces
`WiraDesk-0.1.0-x64-setup.exe` — the `-x64-setup` ending that `release.yml` hands winget as its
`installers-regex`. Nothing Rust changed, so `fmt`, `clippy`, and the test suite were not re-run.

### 2026-08-27 — the signing route researched, and three widely-repeated facts retired

The packaging work landed without an answer to the question that gates it: what signs the
installer. Four routes were checked against primary sources — two Microsoft Learn pages
revised within the last three weeks — rather than against recollection, and three facts
repeated all over the internet turned out to be stale.

**EV certificates buy nothing on SmartScreen, and this closes cheaply.** Microsoft's
`code-signing-options` page carries a call-out box: the behaviour where an EV certificate
granted instant reputation *"was removed in 2024"*, and *"Paying a premium for EV solely to
avoid SmartScreen warnings is no longer justified."* Any plan built on buying EV is working
from pre-2024 facts. Not buying it saves USD 400+/year and costs nothing.

**Azure Artifact Signing is unavailable to this product, and not for the reason usually
given.** It was renamed from Trusted Signing, and the "three years of verifiable
legal-entity history" requirement everybody cites is gone — a Microsoft moderator answered
exactly that question on 2026-08-17, and the current prerequisites list no age clause. What
blocks it is geography: Public Trust certificates reach organisations in a listed set of
countries and individuals in the US and Canada only. Indonesia is in neither list. So the
relaxation is real and irrelevant here, which is worth writing down precisely because the
good news is the part that gets repeated.

**SignPath Foundation is free, issues OV, and this project is probably eligible — but the
Slint branch is a question only they can answer.** Their terms require *"an OSI-approved
Open Source license without commercial dual-licensing for all components"* and no
*"proprietary, non open-source component (especially code published by a maintainer or an
affiliated person/organization)."* This workspace is MIT throughout and is not
dual-licensed, and the parenthetical shows the rule aims at a maintainer laundering their
own proprietary code rather than at third-party dependencies. But `deny.toml` accepts Slint
under `LicenseRef-Slint-Royalty-free-2.0`, which is not OSI-approved, so the question is
asked rather than assumed. Two prices if accepted: the UAC prompt names *SignPath
Foundation* as publisher, and every release needs a manual approval by a named Approver.
Their terms carry no SLA and the page is still headed "Draft", so the wait cannot be
estimated.

**Certum Open Source Code Signing in the Cloud, EUR 49/year, is the paid fallback** — OV,
worldwide, issued to an individual and never to a company, so the publisher name would be a
person. Renewal EUR 29. Verification is a government photo ID, a proof of address, and the
URL of an active open-source project. One thing to confirm before buying: whether SimplySign
can sign non-interactively from GitHub Actions, or whether it needs an OTP from a phone — the
answer decides whether signing runs in CI or on a developer machine, and therefore the shape
of `release.yml`.

**MSIX distribution, where Microsoft re-signs the package, is the only route that removes
the warning entirely -- and this design cannot take it.** MSIX enforces the installing user's privilege level; `allowElevation` is a
restricted capability that requires pre-approval and is reported as very unlikely to be
granted, and even when granted it produces a UAC prompt. `main.rs` refuses to run unelevated
and its own message names why — Windows blocks activating or moving windows owned by
elevated programs — and auto-start is `ONLOGON /RL HIGHEST` precisely so that no prompt
appears. The Store is therefore not a packaging choice here; it is a decision to drop
support for elevated windows, which is a product decision and belongs to G1.

Recorded because the trade is worth knowing rather than because it is recommended: that
same route would delete this product's hardest security problem. With no elevated executable
launched at every logon, `acl.rs` and the stored-path validation stop being necessary, and
the `windows.startupTask` extension removes the scheduled task from the uninstaller
altogether — declarative, visible in Settings, and cleaned up automatically. Store developer
registration also became free for both individuals and companies during 2026, so the
USD 19/99 fees no longer figure in the comparison.

**What no route does is remove the warning on day one.** The only figure Microsoft publishes
is *"several weeks and hundreds of clean installs from a wide audience."* Signing does not
buy silence; it buys accumulation. The mechanism is stated plainly on the SmartScreen page:
reputation for an unsigned binary *"cannot transfer from previous versions"*, so it restarts
at zero on every release, forever.

That last sentence is the one with a scheduling consequence, and it is why the plan below
puts promotion after the first signed release rather than after the first release. A traffic
wave is spent once. Spending it on an unsigned build earns reputation that the next version
discards.

Two smaller corrections, both of which had been assumed in the opposite direction here:
winget does not bypass SmartScreen — no Microsoft documentation claims it does, it is absent
from the code-signing comparison table, and it is a delivery channel, so MOTW still applies
to the binary it fetches. And Smart App Control on Windows 11 blocks unsigned executables
outright rather than warning, for all executables and not only downloaded ones, which is a
stronger argument for signing at all than SmartScreen is.

Sources: `learn.microsoft.com/windows/apps/package-and-deploy/code-signing-options` ·
`.../smartscreen-reputation` · `learn.microsoft.com/azure/artifact-signing/quickstart` ·
`signpath.org/terms.html` · `shop.certum.eu/code-signing.html`

### 2026-08-27 — built the Inno Setup equivalent, and it moved the verdict

`packaging/wiradesk.iss` — a working equivalent of the NSIS script, compiled with Inno Setup
6.7.3, implementing all eight requirements including the awkward one. Marked in its own header as
an evaluation prototype that CI does not build, because two installer scripts where CI builds one
is how a repo ends up shipping the one nobody has read in a year.

The prototype was built precisely to stop `packaging-choice.md` resting on documentation, and it
earned that: **three claims in the first version of that document were wrong or weaker than
stated, and all three were caught by building rather than reading.**

- **R10 was the strongest NSIS argument and it was false.** The document said Inno "needs an
  install step or a third-party dependency" to reach the repo's pinned-and-checksummed convention.
  It needs neither: the official download is on **GitHub Releases**, and Inno's own installer
  supports **`/PORTABLE=1`**, so `ISCC.exe` was obtained in a non-elevated shell with one `curl`,
  one `Get-FileHash`, and one silent run. GitHub Releases is also the steadier host — the NSIS
  download requires knowing that `curl.exe` works where `Invoke-WebRequest` silently gets HTML.
- **R2's margin was overstated.** Inno matched the graceful-shutdown requirement in comparable
  `[Code]`, with `CloseApplications=no` to switch Restart Manager off. NSIS still wins on not
  having to disable a default, but "Inno cannot do this cleanly" was too strong.
- **"More readable" was 17%, not a landslide** — 113 non-comment lines against 136. The real
  difference is the kind of line, not the count.

Measured off the two compiled binaries, identical 17 MB payload:

| | NSIS 3.12 | Inno 6.7.3 |
| --- | --- | --- |
| Installer size | **6.35 MiB** | 8.13 MiB (+28%) |
| Script, non-comment lines | 136 | **113** |
| Manifest | `requireAdministrator` | `asInvoker` |
| Version source | `/DVERSION=` plus a tag-vs-crate check in CI | **read from the binary** |

**The measurement that changed the recommendation** is the last row. `GetStringFileInfo(exe,
"FileVersion")` reads the version out of `wiradesk.exe`, whose resource `build.rs` fills from the
crate version — proven, because the output was named `WiraDesk-0.1.0-x64-setup-inno.exe` with no
version passed on the command line. That does not make the release workflow's version-agreement
step easier; it **deletes the need for it**. Three of Inno's advantages remove ongoing work
permanently (version, upgrade-by-`AppId`, declarative uninstall) while NSIS's remaining
advantages are one-off or immaterial — a 28% smaller download does not compound, a version read
from the binary does.

Verdict revised from "stay on NSIS" to **lean Inno, decide before `v0.1.1`**. Both scripts
compile; this is no longer a capability question. Switching costs about an hour — repoint both
workflows, drop the version-agreement step, delete the other script. Staying costs nothing today.
What is not optional is choosing before release: afterwards the old NSIS uninstaller and a new
Inno installer are unaware of each other and an upgrading user gets two uninstall entries, one
broken.

Inno **6.7.3** rather than 7.1.0 on purpose. 6.7.3 (2026-05-26) is mature and well past
CVE-2025-15595, which affected 6.2.1 and earlier. 7.1.0 landed 2026-08-12 with breaking changes —
architecture identifiers deprecated, Pascal removals, 64-bit installers — and none of its new
capabilities are needed here, so the newer line buys risk and nothing else.

One thing the compiler caught that reading would not have: the `[UninstallRun]` entry needed a
`RunOnceId`, without which it can execute more than once across repeated uninstall attempts.
Harmless for an idempotent `schtasks /Delete`, but the warning was right.

### 2026-08-26 â€” the auto-start task stopped trusting its own stored path

Two defects, one live. `autostart::is_registered` only ever read the **exit code** of
`schtasks /Query` â€” whether the task exists â€” and never compared the absolute path stored in its
`/TR` action against `current_exe()`. On this machine the task was pointing at
`target\release\wiradesk.exe`: a directory whose DACL grants `Authenticated Users` `Modify`, which
an unelevated process was able to write to on the first try. The task runs `ONLOGON` with
`/RL HIGHEST` and no UAC prompt, so that was an unprompted elevated foothold available to any
non-administrator, sitting in the maintainer's own checkout. `SECURITY.md` warns the reader against
exactly this ("do not enable auto-start from a build in `Downloads`") â€” the code offered no check.

**A â€” the stale path.** `refresh_registered_path` re-registers the task from `current_exe()` at
startup whenever one is registered. It rewrites unconditionally rather than reading the stored path
back first, and that is the deliberate call: `/FO LIST` labels are localised, so `Task To Run:` is a
different string on a Windows installed in Indonesian, and `/XML` emits UTF-16 through a pipe. A
guard that silently stops matching on a translated Windows is not a guard. `create_args` already
carries `/F`, so re-creating is idempotent and cannot fail open. It runs **before**
`legacy::migrate_scheduled_task`, which is load-bearing: migration returns early when a task exists
and creates one from the current executable when it does not, so refresh-then-migrate covers the case
migration cannot and stays a no-op in the case it does. The task is written once either way, never
twice. `is_registered` itself is untouched â€” it is the source of truth for the menu checkmark, and a
checkmark going blank because a path drifted would report the wrong thing.

**B â€” the unsafe location.** New `acl` module: reads a path's DACL through
`GetNamedSecurityInfoW` + `GetAce` and answers whether a non-administrative principal holds a right
that would let it replace what is there. Three verdicts, not two â€” `Unknown` is never folded into
`AdminOnly`, because a DACL that could not be read is not one that turned out to be safe. Surfaced
through the existing Tier-2 seam (`log::warn`: one line in `wiradesk.log` plus the latched tray dot,
no modal), at daemon startup and at the moment the tray toggle turns auto-start **on**.

**It warns and does not refuse, by the owner's decision.** Refusing would be the stronger guard and
was offered; running from `target\release` is what building this project looks like, and a guard that
blocks the maintainer's own workflow gets switched off rather than heeded.

we expect*, not *is this path protected*. It would clear a Program Files subfolder whose ACL an
installer had loosened and condemn a correctly-locked `D:\Apps\WiraDesk`.

**The real-DACL test earned its place immediately.** `FILE_REPLACE_RIGHTS` and
`DIRECTORY_REPLACE_RIGHTS` are two masks because bit `0x0004` is two different rights: on a file it

file. Windows grants it to `Authenticated Users` on `C:\`. The first version used one combined mask,
and `a_system32_executable_reads_as_administrators_only` went red on the drive root â€” a false
positive that would have fired on every correctly-installed machine, and all six pure unit tests
around it stayed green. Inherit-only ACEs are skipped for the same class of reason:

### 2026-08-26 â€” Settings is bound to the daemon's lifetime

Requested directly: exiting the daemon must close Settings, including when the
daemon is killed from Task Manager or dies unexpectedly. Settings must not be
alive without a daemon.

Before this, the two processes were fully independent. Settings only asked
whether the daemon was running at one point â€” the Key Check pane's status line â€”
and did nothing about the answer, so a Settings window outlived the daemon
happily: shortcut fields that record nothing (recording needs the daemon's hook
lease, `DEC-004`), a Key Check pane reporting "not running" for every chord, and
a Save that writes `config.toml` and then signals a reload to a window that no
longer exists. Not a degraded window â€” a lying one.

New `crates/settings/src/daemon_watch.rs` holds both halves of the rule:

* **Startup** â€” `startup_decision` refuses to open with no daemon running, with
  a message box that names the way back in (the tray icon) rather than a window
  that appears and vanishes half a second later.
* **Runtime** â€” `DaemonWatch::tick`, driven by a 500ms Slint timer on the UI
  thread, hides the window and quits the event loop on the first tick that finds
  the daemon gone.

Liveness is `FindWindowW` on the daemon's hidden window, not a process handle,
and that choice is the non-obvious part. One probe covers every way the daemon
can stop â€” tray Exit, `ExitProcess`, a crash, `taskkill` â€” because Windows
destroys a dead process's windows either way, so there is no separate
"unexpected exit" path to get right. It also needs no handle to the daemon:
the daemon is elevated, Settings usually inherits that but carries no elevation
manifest of its own, and `OpenProcess` across integrity levels is exactly the
access a watch like this must not be able to fail on. Finding a window is a read
that works either way. Same call the Key Check pane already made, now shared, so
the two answers cannot contradict each other.

The timer closes the window *and* calls `quit_event_loop`. Hiding alone leans on
Slint's quit-on-last-window-closed behaviour; if that ever stops holding, the
process would keep running with no window at all â€” the precise state this watch
exists to prevent.

Escape hatch: `WIRADESK_SETTINGS_ALLOW_NO_DAEMON` waives the startup refusal,
set by `scripts/verify-settings-runtime.ps1`, which drives the real window
through UI Automation and deliberately does not require Administrator â€” so it
cannot start a daemon to satisfy the check. Same shape as
`WIRADESK_SKIP_MANIFEST`: an opt-out a harness sets deliberately.

Note the deliberate omission: a forced close discards an unsaved draft rather
than persisting it. Writing a draft the user never confirmed would be worse than
losing it, and with the daemon gone there is nothing to apply it to.

Eight unit tests over the two pure decisions, all seen red first by making
`tick` never fire and `startup_decision` always open (4 of the 8 failed, the
other 4 being the alive/waiver cases that the mutation leaves true).
`cargo fmt`, `clippy -D warnings`, `cargo test --workspace` (386 tests, +8)
clean. `verify-public-export.ps1` reports only its pre-existing commit-count

### 2026-08-26 â€” Snapped/maximized windows left a gap at the screen edge

Reported directly: snap left/right, maximize, and overlapping stack all
left a small margin at the screen edge instead of using the full work
area â€” worse and more visible on Chromium-based apps (Chrome, Edge,
Electron apps like VS Code/Discord), fine on some other apps.

Root cause: `Win32WindowMover::apply` (`crates/daemon/src/arrangement/win32.rs`)
passed the planned rect straight to `SetWindowPos`, which positions a
window's *outer* rect (`GetWindowRect`). Since Windows 10, most windows
carry a few pixels of invisible, hit-testable resize border that sits
*outside* the visible frame â€” the visible frame is
`DwmGetWindowAttribute(DWMWA_EXTENDED_FRAME_BOUNDS)`, not `GetWindowRect`.
Positioning the outer rect at the work-area edge leaves exactly that
border's width as a gap between the visible window and the edge.
Chromium-based apps draw their own frame and tend to carry a larger,
more visible instance of the same gap, which is why the symptom reads as
"some apps, not all."

Fixed with the standard compensation (the same shape PowerToys FancyZones
and other snap tools use): before `SetWindowPos`, `frame_insets(hwnd)`
measures the gap between `GetWindowRect` and the extended frame bounds for
the actual target window, and `compensate_for_frame_insets` widens the
planned rect outward by exactly that gap, so the *visible* frame lands on
the intended rect instead of the outer rect landing there. Best-effort:
a failed query (no DWM, closed window) degrades to zero insets â€” the
placement still lands, just without compensation, which is the behaviour
this file always had before.

Four new unit tests cover the pure geometry (`FrameInsets::from_rects`,
`compensate_for_frame_insets`) including the inverted-frame clamp (Windows
makes no promise the extended frame is never larger than the outer rect).
Not covered by a test: the live `GetWindowRect`/`DwmGetWindowAttribute`
query itself, which needs a real window and is exercised only manually.

`cargo fmt`, `clippy -D warnings`, `cargo test --workspace` (378 tests,
+5 for this) clean.

### 2026-08-21 â€” the bypass check got a test seam, so the suite stopped reading the desktop

`handle_key_event` asked the OS whether the foreground window belonged to a VM or Remote Desktop
guest the moment a chord matched. That is right in production â€” the question has no other answer â€”
but two unit tests called it directly, so with no resolvable foreground window the bypass failed
open, the matched chord returned pass-through, and both tests failed. They passed or failed
according to what had focus, and on a CI runner with no interactive desktop they would fail every
run.

Split into a thin `handle_key_event` wrapper plus `handle_key_event_with_bypass`, which takes the
check as an `FnOnce(&mut HookRuntime) -> bool`.

boolean would have forced the live Win32 query to happen *before* the function knew whether a chord
had even matched â€” adding an OS call to every key event, on the one thread that must finish inside
`LowLevelHooksTimeout`. Deferring it keeps the call exactly where it was: after the match, on a rare
path. The generic is monomorphised, so the seam costs nothing at runtime.

Production behaviour is unchanged; the wrapper supplies the real call. The two tests pass `|_| false`
and keep every assertion and expected value they had â€” they guard the sticky-modifier bug, where a
swallowed Win key-up left the focused application treating every later keystroke as Win+key, so
weakening them to get green would have thrown away the guard and looked like a fix.

## Plans

### Ship the first release, with updating already in it

Nothing has been released. `git tag` is empty, so no user holds an installer from this
repository, and neither `packaging/wiradesk.nsi` nor `packaging/wiradesk.iss` has ever been
run — both compile, and that is not the same claim.

**Two install channels, and one update mechanism that serves both.** The channels are the
standalone installer from GitHub and the website, and winget. They do not need separate
update machinery and must not be given any, because both write the same Add/Remove Programs
entry and that entry is what every version comparison reads. After an in-app update the ARP
version is the new one, so `winget upgrade` correctly reports nothing to do; when winget
performs the upgrade instead, the in-app check sees the new version for the same reason.
Detecting which channel installed the product was considered and rejected: winget runs the
same installer, so the installer cannot tell, and every available heuristic is fragile enough
to produce wrong behaviour in the one case it matters.

What differs per channel is only who initiates. winget users run `winget upgrade`, which the
release workflow already serves and which needs no code here. Everyone else uses the in-app
updater, which is the part that has to be built.

**The user-facing update path is not winget.** The release-notes block in `release.yml`
currently reads *"To update later: winget upgrade WiraDigitalIndonesia.WiraDesk"*, which
presents a command line as the update path for a consumer desktop application. That text is
wrong and is corrected as part of the work below. winget remains a discovery and installation
channel, and it is a good one; it is not the answer to how a user updates.

Three orderings are load-bearing. Everything else can move.

**Gate 1 — CLOSED on 2026-08-27: Inno Setup, and the NSIS script deleted.** The rule it
enforced, kept here because it still explains the deadline that shaped everything else — the
engine had to be chosen before the first tag, or not cheaply at all. Whichever of
NSIS and Inno Setup survives, the other script is deleted in the same change. Today the
choice costs nothing because there is no installed base; after the first tag, switching means
the old uninstaller and the new installer do not know about each other, and a user who
upgrades ends up with two Add/Remove Programs entries, one of them broken. The comparison is
in `docs/packaging-choice.md` and its verdict leans Inno, on one reason: `GetStringFileInfo`
reads the version out of the built binary, so the installer cannot disagree with the program
it installs, and the tag-versus-crate step in `release.yml` stops being needed at all.

**Gate 2 — the updater ships in the first release, so it is built before the tag.** The
requirement is that the first version anyone installs can already update itself; a release
without it strands its own users. This has an awkward consequence that must be handled
deliberately rather than discovered: the updater cannot be proven against a real release
until a second release exists, so it will ship unverified unless it is tested before the tag
against a stand-in `latest.json` served from somewhere disposable. That test is a work item,
not an optional nicety.

**Gate 3 — promotion waits for the first signed release.** See the Progress entry above for
the mechanism. Publishing quietly first is not a compromise: SignPath requires that *"The
project must already be released in the form that should be signed"*, so a release has to
exist before the application can be made. Publish first, apply second — they are sequential,
not parallel. The download page on wiradigital.id is application material too, because the
same terms require the project's functionality to be described there.

The sequence, then:

1. **Changelog and the version chain.** Gate 1 is closed. Rewrite `CHANGELOG.md` into Keep a Changelog form with dated
   headings, add a `release.yml` step that refuses a tag with no matching changelog section,
   and add a bump script covering the three places a version lives — `Cargo.toml`,
   `crates/daemon/wiradesk.rc`, `crates/settings/wiradesk-settings.rc`, the last two copied
   by hand today and held together only by `version_resource_matches_cargo_manifest`. Release
   notes come from the changelog section and must keep carrying the Slint attribution, which
   is a licence term rather than a credit.
2. **Run the installer on a real machine.** Install, enable auto-start, reboot and confirm the
   daemon starts with no prompt, run the installer again over the existing install and confirm
   one uninstall entry rather than two, then uninstall and open Task Scheduler to see the task
   actually gone. Silent install and uninstall are on the list because both winget and the
   updater depend on them. This needs elevation and cannot be done from a CI runner.
3. **Build the in-app updater.** Visible, never silent: the user clicks, sees a download
   progress bar, consents to one UAC prompt, and watches the installer's own progress window.
   Awareness is a requirement, not a side effect. Verification is tiered because the
   certificate does not exist yet — SHA-256 against `latest.json` over HTTPS now, and an
   Authenticode check with a publisher-subject match promoted to a hard refusal when the
   certificate lands. No new dependency is needed: `Win32_Networking_WinHttp`,
   `Win32_Security_WinTrust`, and `Win32_Security_Cryptography` are all features of the
   `windows-sys` version already in the tree, and `serde_json` is already in `Cargo.lock`.
   `PRIVACY.md` has to be corrected first — it currently promises *"There is no socket, HTTP
   client, or update check in the source"*, which this feature makes false, and a published
   promise is not a detail. The check itself must be opt-in and default off; only the version
   comparison must accept a strictly greater version, so that a replayed older `latest.json`
   cannot push a superseded build.
4. **Prepare the installer for being driven by the updater.** Three defects sit on this path
   today and two of them are certain to fire, because they exist only in the silent code path
   that nothing but an updater uses. The daemon is never restarted after a silent install —
   `packaging/wiradesk.iss` flags the restart step `skipifsilent`, and NSIS's
   `MUI_FINISHPAGE_RUN` runs only on a finish page that silent mode never shows — so the user
   would click Update and watch the application disappear; the fix is for the updater to
   relaunch the daemon once the installer exits. And both scripts run
   `taskkill /IM wiradesk-settings.exe`, so an updater living inside Settings is killed by the
   installer it started; the fix is to launch the installer detached and let Settings exit.
   Run the installer with `/SILENT` rather than `/VERYSILENT`, so progress stays visible
   without asking the user questions they already answered.
5. **Tag the release, GitHub only.** Leave `WINGET_TOKEN` unset so the winget job skips
   itself; the first manifest pull request is manual and sits in someone else's review queue,
   which does not belong in the release that exists to prove this pipeline. Install the
   artefact downloaded from the release page, not the one built locally.
6. **Check for detection, not just for a warning.** This product's shape — a new unsigned
   binary that requires elevation, installs a global keyboard hook, and registers an
   `ONLOGON /RL HIGHEST` task — is the silhouette of a keylogger. If Defender labels it PUA or
   malware, the WDSI portal's "incorrectly detected" path is the one that helps; its
   reputation-review path does not, and Microsoft says so.
7. **Download page.** Publish `latest.json` as a release asset so
   `releases/latest/download/latest.json` is a permanently stable URL — no API, no rate limit,
   and it solves the problem that the installer filename carries a version and therefore
   cannot sit behind a stable link. It is the same file the updater reads, so it has one
   schema and one publisher. The page reads it too. The binary is linked, never copied to the
   VPS: two copies of an `.exe` are two things that can differ.
8. **Apply to SignPath**, stating the Slint question openly rather than hoping it is not
   noticed.
9. **When the certificate arrives.** Sign the installer and the uninstaller, sign both
   binaries, promote the updater's Authenticode check from advisory to mandatory, and correct
   the two places that state the binaries are unsigned — `SECURITY.md` and the release-notes
   block in `release.yml`. Verify with `Get-AuthenticodeSignature` on the published artefact
   rather than the local build.
10. **winget.** A fork of `microsoft/winget-pkgs`, a **classic** personal access token with
    `public_repo` stored as `WINGET_TOKEN` — fine-grained tokens are not supported by the
    action — and one manual first manifest. Then verify `winget install` and, separately,
    `winget upgrade` from the previous version, because that is the path a winget user takes.
11. **Promotion.** Drafts are in `personal-notes/content-strategy/windows-installer-article/`.

Not decided, and deliberately left open: which process hosts the updater.
`crates/settings/wiradesk-settings.rc` deliberately carries no manifest so Settings does not
request elevation, but the daemon launches it with `ShellExecuteW` and it therefore inherits
an elevated token today. That matters here more than it did before: an elevated process that
downloads and executes an installer is a materially worse shape than an unelevated one that
asks for consent, so the updater's home and the elevation it inherits are one decision rather
than two.
